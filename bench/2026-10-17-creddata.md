# External benchmark: PPE rules, Gitleaks and detect-secrets on Samsung CredData (2026-10-17/18)

> **Pre-alpha.** The first secrets dataset through `ppe evaluate`, and the first one that is real
> source code: 11,030 files from 337 open-source repositories, with lines that secret scanners flagged
> reviewed by people. Same scorer as the Nemotron and Gretel runs
> ([`2026-10-16-nemotron-pii.md`](2026-10-16-nemotron-pii.md),
> [`2026-10-16-gretel-pii-finance.md`](2026-10-16-gretel-pii-finance.md)). It measures how many real
> credentials PPE's Stage 1 secret rules find and how much they report on ordinary code (review finding
> F-02), against Gitleaks and detect-secrets, the established secret scanners listed in
> `docs/sources/detector-models.md`. On 2026-10-18 Gitleaks' rules were imported into PPE (v0.1.0.dev2),
> then PPE's own rules were revised (secret rules v3: Basic, Bearer and NTLM credentials, a narrower placeholder
> filter); every PPE result here is from v3.

Results: `bench/results/2026-10-17-creddata/`. Presidio (the personal-data baseline of the Nemotron
and Gretel runs) has no secret recogniser and, on a 1,000-file sample, reported a span every 200
characters of code, mostly identifiers read as names or organisations; it is not a useful comparison
for secrets, and its sample results were not kept.

## In short

- **PPE now finds 0.516 of the credentials, and 0.686 of its secret spans are credentials**, without the
  largest file (see below). Before the Gitleaks import: 0.325 and 0.449; v0.1.0.dev2: 0.441 and 0.664. On
  all files: 0.593 and 0.753.
- **One test file of cryptographic test vectors** (`Key = <hex>`, 2,865 lines, 18% of every credential)
  decides full-dataset rankings on its own; every comparison below is also given without it.
- **The baselines, without that file**: Gitleaks finds 0.338 (0.762 of its spans are credentials),
  detect-secrets 0.370 (0.342). PPE now finds more than either; Gitleaks' rules alone are still more
  precise (0.762), because PPE keeps its own `KEY=value` rule for short and simple passwords.
- **Basic, Bearer and NTLM credentials are now found**: of the credentials labelled Basic, Bearer and NTLM,
  689 of 692, 289 of 289 and 108 of 126 are covered; the three new rules put 40 spans on unlabelled
  lines and 1 on a line reviewed as no credential.
- **PPE's copy of Gitleaks' rules matches Gitleaks**: 8,287 of Gitleaks' 8,350 findings; 20 of the
  rest are rules that need a file path, the others small (decoding, file chunking, positions).
- **Credentials with a known vendor prefix are the solved part**: PPE 0.996, detect-secrets 0.936,
  Gitleaks 0.879.
- **Generic secrets are still not solved by anyone**: PPE misses 6,408 credentials, 3,013 of them
  keys, passwords, tokens or auth values without a fixed format.
- **CredData flatters placeholder and entropy filters**: true values are replaced by random strings
  that never contain a dictionary word or a keyword ("Obfuscation"). On Nemotron, whose passwords are
  not scrambled, v0.1.0.dev2's placeholder filter (Gitleaks' word list) dropped 44 real passwords; the
  v3 filter drops 2.

The data lives outside the repository and is never committed.

**Label rule, fixed before any system was scored on this dataset** (`CREDDATA` in
`src/prompt_privacy/evaluation/datasets.py`). Each gold span is labelled `<verdict>:<rule names>`
(`T:Password`, `F:Key:Token`). Every `T:` label maps to SECRET, whatever the rule: CredData's T means
"a real credential". `X:` labels are compatible with SECRET: a SECRET span there is neither a hit nor a
false positive, and they are not support. `F:` labels are unmapped: a SECRET span on a reviewed
non-credential line is a false positive. The scorer gained label prefixes for this (an exact label
entry still wins); Nemotron and Gretel reports are unchanged in form.

**What precision means here.** Only lines that scanners flagged were reviewed. A SECRET span on an
unlabelled line counts as a false positive, though it may be a credential no scanner flagged. Spans of
other types (e-mail, IP, phone, card) have no labels at all in this dataset; they are counted, not
scored. Precision "any label" counts spans on F lines as hits, so read typed precision.

**Obfuscation.** CredData replaces every true value with a seeded random string of the same shape and
keeps vendor prefixes (`AKIA`, `ghp_`, `eyJ`, `-----BEGIN`); checksums inside tokens are not kept, so a
rule that checks a token's checksum would miss obfuscated values the real ones would pass (no rule
used here checks one). The replacement is drawn again until it contains no `api`, `key`, `pass` or
`pwd`, no character four times in a row and no run like `abcd` or `9876`
(`obfuscate_creds.py`, `generate_value`). So a true value never looks like a placeholder or a
low-variety string, while F values are left as they were. A tool that drops low-entropy or
placeholder-like values (Gitleaks, detect-secrets, and now PPE) loses fewer T values here than on real
code, where real passwords such as `admin123` occur. On Nemotron's synthetic but unscrambled passwords
the cost of PPE's placeholder filter is measured (`assignment-filters.txt`): Gitleaks' word list
dropped 44 of 246, the v3 filter 2.

## Gitleaks' rules in PPE (2026-10-18)

**What was imported.** Gitleaks 8.30.1's default rule file, unchanged and pinned by SHA-256
(`src/prompt_privacy/detectors/gitleaks_rules/`, MIT; NOTICE), applied by `detectors/gitleaks.py` as
Gitleaks applies it: keyword prefilter, secret group or first non-empty group, entropy above the
threshold, global and per-rule allow-lists (secret, match or line; stop words; AND/OR), and the
generic-rule dedupe. 217 rules load; 5 need a file path and are skipped, since a prompt has none. A
`gitleaks:allow` comment does not exempt a line in a prompt. Any rule-file key the loader does not
implement is refused at load, so an updated rule file cannot silently change meaning.

**Engine (operator decision 2026-10-18): RE2, a required dependency** (`google-re2`, BSD). The rules
are Go regexes; RE2 runs them unmodified with Go's semantics and in linear time. On adversarial inputs
(every rule against 14 hostile 20,000-character texts) Python's `re` took 43.6 s in total and up to
1 s per rule and text, with 25 rules needing translation; RE2 took 0.14 s, at most 4 ms. With every
keyword present, all rules on 200,000 characters took 0.07 s here (a test; it allows 5 s).

**Fidelity** (`gitleaks-fidelity.txt`, `gitleaks_fidelity.py`; PPE's copy of the rules alone, no PPE
rules, against Gitleaks' own spans): 8,281 same span, 6 overlapping, 15 PPE only, 49 Gitleaks only.
Of the 49, 20 come from the rules that need a file path (Terraform, Kubernetes). The other 29 (12
private keys, 16 generic, 1 curl) and the 15 PPE-only spans (8 generic, 6 Sourcegraph, 1 curl) were
not examined one by one; the known causes are Gitleaks' decoding of base64, hex and percent-encoded
text before matching (PPE does not decode), Gitleaks reading a large file in fragments (its keyword
prefilter then sees one fragment, PPE the whole text), and the 30 Gitleaks values the converter could
place only on their whole line(s).

**How PPE's own `KEY=value` rule (`assignment`) fits in** (operator decision 2026-10-18: measure, then
choose). Four set-ups, scored without the largest file:

| set-up | found | P typed | spans |
|---|---:|---:|---:|
| A: Gitleaks' rules plus `assignment` | 0.443 | 0.485 | 13,142 |
| **C1: A, with `assignment` values that contain a Gitleaks stop word dropped (v0.1.0.dev2)** | **0.441** | **0.664** | **8,882** |
| C2: C1, plus Gitleaks' other generic allow-lists (no entropy test) | 0.394 | 0.647 | 8,051 |
| B: Gitleaks' rules instead of `assignment` | 0.362 | 0.726 | 6,531 |

C1 drops 4,260 spans for 21 credentials (CredData) against A; against B it finds 1,023 more
credentials. `assignment` keeps no entropy floor, so short real passwords still count; the stop words
are the global allow-list's and the generic rule's (1,448). The cost on unscrambled passwords is
measured on Nemotron: 44 real passwords dropped. The filter also cleared two of the code snippets in
conformance check C-07 (`password = form.cleaned_data[...]`, `token = get_token(...)`). Replaced by
the v3 filter below.

## PPE's own rules revised: secret rules v3 (2026-10-18)

**A narrower placeholder filter for `assignment`** (`secrets.is_placeholder`). Gitleaks' 1,448 words
include ordinary programming words, so they drop real passwords such as `account123` (44 on Nemotron).
v3 drops a value only if it holds a placeholder word (`change`, `example`, `sample`, `dummy`, `fake`,
`placeholder`, `your`, `xxx`, `todo`, `fixme`, `redacted`, `replace`, `insert`) or a word naming a kind
of credential (`token`, `passw`, `secret`, `auth`, `access`, `credential`: `ACCESS_TOKEN=access_token`),
is a template (`${X}`, `{{x}}`, `<x>`, `$X`, `%X%`), has three or fewer distinct characters, or, when
not quoted, contains a call or an index (code: `os.environ[`, `get_token(request)`). The
placeholder words were fixed before measuring; the credential-kind words and the code test were chosen
after reading which Gitleaks words removed most spans on CredData's F lines, so CredData flatters them;
Nemotron's passwords played no part in the choice. Spans kept on the same candidates
(`assignment-filters.txt`, `assignment_filters.py`):

| filter | CredData T | F | X | no label | Nemotron `password` |
|---|---:|---:|---:|---:|---:|
| none | 2,304 | 2,807 | 595 | 2,623 | 246 |
| Gitleaks stop words (v0.1.0.dev2) | 2,285 | 1,284 | 136 | 363 | 202 |
| placeholder words, templates, code | 2,302 | 2,125 | 490 | 1,297 | 246 |
| **+ credential-kind words (v3)** | **2,299** | **1,445** | **117** | **306** | **244** |
| + an unquoted letters-only value is an identifier (rejected) | 2,081 | 1,292 | 105 | 214 | 244 |

v3 keeps 14 more credentials than Gitleaks' list on CredData and 42 more Nemotron passwords, for 104
more spans on F and unlabelled lines. The letters-only test was rejected: 218 real credentials lost. A
narrower code test (a name followed by a call) was tried and dropped: 517 unquoted bracket values it
kept held 1 credential. Costs that remain: `Password123`-style values (2 on Nemotron), unquoted
passwords with a bracket (1 on CredData, 1 on Gretel). It also clears the environment-lookup snippet of
C-07 (`API_KEY = os.environ['API_KEY']`).

**Basic, Bearer and NTLM schemes**: three rules, each with a value check (`secrets.VALUE_CHECKS`), with or
without an `Authorization:` name before them. CredData's shapes decided the checks: every Basic
credential labelled T decodes from base64 to `user:password` and none of the 555 labelled F does;
every Bearer token has letters and digits and 16 or more characters; every NTLM credential starts with
the base64 of `NTLMSSP` (`TlRMTVNTUA`).

| rule | value check | on T | on F | no label |
|---|---|---:|---:|---:|
| `basic_auth` | base64 of printable `user:password` | 689 | 0 | 4 |
| `bearer_token` | 16+ characters, letters and digits | 165 | 1 | 5 |
| `ntlm_negotiate` | NTLM (`TlRMTVNTUA`) or SPNEGO (`YII`) prefix | 108 | 0 | 31 |

On the prose datasets they add one span on no gold value (Gretel: 667 → 668 no-gold spans); on
Nemotron, the Bearer rule finds API keys written after `Bearer`.

**Coverage by rule name, before → v0.1.0.dev2 → v3** (T labels, any-type coverage; a label with several
rule names counts for each; `Key` includes the largest file's 2,865): Basic Authorization 0.000 → 0.007
→ 0.996, Bearer Authorization 0.080 → 0.100 → 1.000, NTLM Token 0.000 → 0.000 → 0.857, Auth 0.052 →
0.145 → 0.759, Key 0.055 → 0.866 → 0.867, Token 0.202 → 0.559 → 0.562, Secret 0.742 → 0.859 → 0.863,
API 0.281 → 0.423 → 0.427, Password 0.339 → 0.358 → 0.359, UUID 0.028 → 0.097 → 0.097. PEM private
keys, JWTs and URL credentials stay at 0.96-1.00. Any-type coverage of all T labels: 9,431 of 15,753 =
0.599.

**Other datasets** (regenerated with v3): Nemotron SECRET recall 0.062 → 0.151 at typed precision 0.981
(generic `api_key` values 64 → 1,081 found; passwords 246 → 257), Gretel 0.178 → 0.293 (passwords 6 →

## Everything else PPE reports on code

CredData labels no personal data, so these are counts, not precision. On 1.015 billion characters of
source code, PPE's rules reported:

| type | phone optional | phone required |
|---|---:|---:|
| EMAIL | 33,362 | same |
| IPV4 | 19,052 | same |
| PHONE | **10,499** | **327** |
| IPV6 | 4,454 | same |
| CARD | 543 | same |
| IBAN | 25 | same |

Many e-mails in code are real (author headers, maintainers), so these are not all false positives.
Phone numbers in code mostly are: `required` cuts phone spans by 97% (10,499 → 327). IPv4 and IPv6 on
code include version strings and constants; F-02 asks for a negative code corpus to measure that, and
these counts are the first size estimate of the problem.

## Checks on this run

- **Fidelity** of the imported rules against Gitleaks itself: above (8,287 of 8,350 agree; 20 of the
  differences are the skipped path rules, the rest have known candidate causes).
- **Totals reconcile**: the scorer (`ppe-rules-phone-*.json`), `miss_shapes.txt` (9,345 found, 6,408
  missed), `secret_breakdown.txt` (12,668 spans) and `secret-scanners-overlap.txt` agree for PPE;
  `score_spans.py`, `creddata_overlap.py` and `creddata_secret_breakdown.py` agree for the scanners.
  The v0.1.0.dev2 set-up reproduced the C1 measurement exactly.
- **Scanner runs are offline**: inside the namespace, a request to github.com fails to resolve.
- **detect-secrets in parallel**: the three-process version of the adapter wrote byte-identical spans
  to the single-process run (44 min with the cores shared, against 90).
- **Mutation check** (`mutate_evaluation.py`, Presidio venv, `mutation.txt`): 52 of 52 faults caught,
  6 of them in secret rules v3 (value checks skipped, credential-kind words, code test on quoted values,
  template test, Basic without `user:password`, bearer without a digit). The first v3 run missed all
  six (the new test file was not in the script's list); the next missed the template test (every test
  template also held a credential-kind word), so templates without one were added. 14 are in the
  Gitleaks import (rule-file hash, unknown keys, path-bound rules, keyword prefilter,
  line-break trim, secret group, group order, entropy `<=` and bytes, stop words on the secret, AND
  allow-lists, path checks, generic dedupe, rules not run). The first run missed
  "last non-empty group instead of the first": the test had no case with two non-empty groups; one was
  added. The script now runs tests with `python -B`, after a same-size mutant edited and restored
  within one second left its bytecode in use.
- **Leak scan** (`leak_scan.py`, per dataset, each with a planted control of real dataset text that was
  caught, exit 1): every CredData result file and this page share no run of document text with
